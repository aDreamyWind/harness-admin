# MCP 中台与网关方案（分阶段实施）

本文记录已确认的目标与分阶段实施边界；具体已交付接口以 OpenAPI 和 README 为准。此前“只登记无密钥 HTTP MCP、Admin 不代理调用”的草案已被后续需求取代。Skill 另行设计，不与本期 MCP 的数据模型和交付范围混在一起。Harness Admin 保持模块化单体；运行第三方 MCP 代码时可以使用受隔离的子进程或容器，但不拆业务微服务。

## 一、目标和三段链路

Admin 既能登记现有 MCP 服务，也能从仓库或代码包部署 MCP，并统一展示工具、执行测试、生成对外连接、授权与统计。MCP 不仅服务 Harness，也作为 AI 中台资源供业务应用使用；员工原有的本地、项目自带 MCP/Skill 不因此被禁用。

```text
Harness 员工 / 开发者应用 → Admin 对外 MCP 网关 → 上游 MCP 服务 → 后端业务系统
       入口身份与授权             每条连接的上游配置       MCP 自身的业务凭据
```

“创建服务”解决上游在哪里、怎么运行；“生成连接”解决谁能从哪个入口使用，以及这一入口采用何种上游凭据。服务可产生多条连接。外部调用始终先到 Admin 网关，网关负责入口鉴权、授权、转发和审计，不能把上游密钥或内部地址直接发给客户端。

## 二、服务来源、部署与工具

1. **接入已有服务**：在同一“服务配置”区域选择 Streamable HTTP 或 SSE、填写上游 URL、定义需要的请求头／查询参数／路径参数及其说明；也可粘贴 MCP JSON 配置导入传输方式、地址和字段名。服务不要求填写这些字段的值，每条连接生成时再独立填写并加密保存。不强迫管理员判断业务密钥是在 Admin→MCP 还是 MCP→业务系统这一段使用，界面说明实际注入位置。当前已实现远程 HTTP/SSE 的多项 Header、URL 参数和路径参数；环境变量与 Stdio 随容器运行器实现。
2. **在本项目部署**：从完整 GitHub／Gitee 仓库地址选择分支、标签或提交（自动固定到提交号），或上传本地代码包；包根目录 README.md 自动成为服务描述。服务端负责构建、启动、停止、重启和版本回滚；不接受把管理员电脑的本地目录路径当成服务器可访问的路径。Go 原生工具可在单体内按模块实现；任意第三方 Node/Python/可执行程序在受隔离运行时执行。已确认生产环境可提供 Docker 或等价容器隔离，后续部署能力据此实现。
3. **工具发现与测试**：建立上游会话后调用 `tools/list`，保存工具名称、说明及输入 schema 的快照和刷新时间。管理员可填写参数执行 `tools/call` 测试，显示原始结果、耗时及错误。测试可能造成写入或外部动作，界面必须明确提示，并计入审计与统计。
4. **健康与运维**：显示连接状态、最近发现时间、运行日志和失败原因；支持重新发现、重启、停用。失效服务不能继续生成可用连接。

Stdio 是本机子进程标准输入/输出，不是一个 URL。远程客户端要以 Stdio 方式使用 Admin 网关，必须在客户端安装本地桥接程序；它把标准输入/输出转换成 Admin 的 HTTP MCP 请求。对外优先提供 Streamable HTTP，兼容 SSE，Stdio 桥接作为后续交付。

## 三、统一生成连接，分两种用途

每条连接有系统自动生成的独立内部编码、状态、用途、所属服务、创建者、公开网关地址、上游配置引用及统计归属。不同连接可以使用不同的上游 Authorization、API Key、查询参数或环境变量，不能共享一份可被另一连接覆盖的运行态凭据。开发者连接建议按应用/项目分别创建，便于单独统计、轮换和停用；这不是强制约束，多个应用可以共用连接，但其调用统计与管理影响范围也会合并。

| 项目 | Harness 连接 | 开发者/应用连接 |
| --- | --- | --- |
| 调用者 | 已登录的员工；Web 与桌面 Harness 使用同一规则 | 一个业务应用或项目；其最终消费者可为 ToC 用户 |
| 入口鉴权 | 现有企业 OIDC 用户访问令牌，建议单独增加 `mcp.invoke` scope | 可选应用级 Bearer 密钥，或管理员显式发布的无鉴权连接 |
| 可见与授权 | 按明确选中的部门、用户授权，调用时再次校验 | 按连接是否启用、密钥与有效期校验，不要求识别终端用户 |
| 有效期 | 跟随用户会话令牌；连接本身也可停用 | 生成时选择有效期；过期、停用或轮换密钥立即生效 |
| 统计归属 | 连接、工具、用户及调用时部门快照 | 应用/项目、连接、服务、工具；不强求 ToC 用户身份 |
| 下发方式 | Harness 登录后自动获取获准连接与配置，员工无需逐项填写 | 管理员复制生成的 URL/配置给业务系统接入 |

部门选择沿用现有组织树交互：勾选父部门时默认勾选**当前**所有子部门，随后可以单独取消；保存的是最终勾选的部门 ID，不对未来新增的部门自动继承。用户授权可补充单独允许/撤销；多条规则冲突时建议明确拒绝优先。Harness 登录后的资源目录与每次实际 `tools/list`、`tools/call` 都要在服务端按当前组织关系和策略判断，不能只靠客户端隐藏。

对开发者连接，“无鉴权”并不等于“无统计”：网关仍可按连接编码统计调用，但无法可靠识别具体调用者，因此不声称能按部门或个人授权/计量。无鉴权只允许管理员显式发布，默认关闭，建议设置到期时间、速率上限和审计；不能把不可猜测的 URL 当成身份认证。应用级 Bearer 密钥只能证明“是哪条应用连接”，也不能识别该应用内部的 ToC 用户。

## 四、凭据如何放置

1. **客户端→Admin**：Harness 带当前员工的 OIDC Token；开发应用带本连接的 Bearer 密钥，或按明确配置无鉴权。这是“对外连接鉴权”。
2. **Admin→MCP**：上游服务若要求 Authorization/API Key，管理员或连接创建者为该连接配置，由网关在发给上游的请求中注入。不能直接把员工 OIDC Token 传给任意上游 MCP；若某个上游必须做用户委托，应单独实现它认可的 OAuth 授权流程。
3. **MCP→业务系统**：MCP 程序所需业务 API Key 通常以它要求的环境变量、启动参数或私有配置注入。管理员只需在“上游配置”中按该服务说明填写；系统负责以正确方式交给运行时，不把它暴露到对外配置里。若 MCP 服务要求每位调用者分别提供业务凭据，需要另设计用户凭据授权/委托，不能假装共享密钥已实现这一点。

密钥持久化加密、按权限再次查看并记录查看审计；响应和日志默认脱敏。Stdio 程序若通过进程环境变量读取密钥，不同连接应有独立进程/隔离运行实例，仅数据库分开存储不够。HTTP 上游则须保证请求头、会话和缓存按连接隔离。密钥轮换、停用和删除后旧连接不得继续使用。

## 五、传输与接口契约

| 方向 | 首批目标 | 后续兼容 |
| --- | --- | --- |
| Admin 接上游 MCP | Streamable HTTP、SSE；受控 Stdio 运行器随部署能力落地 | 上游 OAuth、更多扩展 |
| 客户端接 Admin 网关 | Streamable HTTP 的稳定网关 URL | SSE 网关兼容端点、可下载/安装的 Stdio↔HTTP 本地桥 |

建议的员工目录接口为 `GET /api/v1/mcp/connections`，只返回当前登录员工有权使用的连接元数据和公开网关 URL，不返回任何上游密钥。建议的网关入口为 `/mcp/{connection_code}`；准确路径、协议版本、Web/桌面 Harness 的重载方式须在与 Harness 对齐 OpenAPI 后冻结。开发者连接可生成配置片段与复制按钮。无论使用哪种传输，MCP 会话、身份及上游配置都必须按连接隔离；调用中途撤权/停用不能继续执行后续工具请求。

首批明确支持 `tools/list`、`tools/call`，不要对外宣称尚未实现的 resources、prompts 或采样能力。流式响应与错误语义按实际实现的 MCP 协议契约测试；若使用 SSE 兼容端点，说明其兼容范围。

## 六、数据模型与统计

建议从下一条迁移 `00021` 起新增如下逻辑实体；最终名称以现有仓库命名规范为准：

| 实体 | 主要内容 |
| --- | --- |
| MCP 服务 | 企业、编码、名称、来源类型、上游传输、来源 URL/固定提交、状态、默认非密配置 |
| 部署/运行实例 | 服务版本、构建产物引用、启动配置、运行状态、隔离实例及最近错误 |
| MCP 工具快照 | 服务/版本、工具名称、说明、输入 schema、最近发现时间 |
| MCP 连接 | 服务、用途（Harness/开发者）、所属应用或项目、编码、有效期、状态、网关配置 |
| 连接凭据 | 入口密钥的校验摘要/可审计的加密值、上游密钥加密值、轮换版本及注入位置 |
| 连接授权 | 明确列出的部门/用户及允许或拒绝策略，仅用于 Harness 连接 |
| 调用记录/聚合 | 连接、服务、工具、时间、结果、耗时；Harness 另存用户和部门快照 |

开发者连接只做每应用/连接/工具调用次数、成功失败、耗时及必要流量统计；不要求追踪应用的每位终端用户。Harness 连接统计到用户与部门。MCP 本身不天然提供“模型 Token 用量”，只有 MCP 或下游明确返回可信用量时才能作为附加指标，不能从工具调用次数推算 Token。详细调用记录和聚合、保留期限应有配置，敏感入参/返回内容默认不入库。所有新表和字段补简体中文 `COMMENT ON TABLE/COLUMN`。

## 七、界面与安全边界

页面在“AI 资源管理”下只保留一个“MCP 管理”二级菜单。左侧按名称与传输类型列服务，右侧上方展示服务描述、连接及接入示例，下方展示工具列表和测试；服务支持修改，调用统计入口位于每条连接操作中，统计页只展示该连接的数据。沿用现有菜单的紧凑标题和布局风格，不采用“大标题 + 说明文字”模板。生成连接时先选用途，再呈现对应的入口鉴权、期限或部门/用户授权选项，以及服务定义的参数值字段；请求上限可选，不填默认 60 次／分钟。

安全要求：远程上游 URL 防 SSRF 与内网越权；仓库导入锁定提交并检查依赖/构建来源；第三方运行时限制文件系统、网络出口、CPU/内存/时间、并发及日志；工具测试提示副作用；入口按连接限流并保留审计。运行第三方代码所需容器/沙箱环境需在部署方案中写明，不能仅凭 Go 语言就认为导入任意 MCP 可以安全运行。

## 八、实施顺序与验收

1. 冻结对象边界、OIDC scope、Harness Web/桌面目录与重载契约、OpenAPI 和权限语义；确认受控运行环境。现有草案不直接作为已发布接口。
2. 做迁移、业务模块、管理员界面与基础审计；先接入现有 HTTP/SSE MCP，工具发现和测试，完成 Streamable HTTP 网关。
3. 做 Harness 连接目录/部门用户授权/每次调用校验，以及开发者应用连接、密钥/无鉴权/有效期；完成各自统计与撤权、轮换测试。
4. 做 GitHub 固定版本及本地代码包部署、隔离 Stdio 运行器、独立凭据实例、构建与运维；验收一个真实 MCP 工具的端到端调用。当前初版已实现公开 GitHub／Gitee 仓库完整地址、自动解析固定提交、根目录 README.md 服务描述、`.tar.gz` 上传、受限 Docker 构建与运行、版本记录、启停重启、日志和回退，并接入现有工具发现与网关。Node.js 可预检仓库的构建命令与入口，也可在导入时留空自动识别；构建容器安装开发依赖、断网执行 `npm run build`，编译后验证入口并裁剪开发依赖。已使用真实公开 GitHub 仓库 howtocook-mcp 的固定提交完成 Docker 构建、启动、MCP 握手、5 个工具发现及管理员侧只读工具调用；开发者 Bearer 连接也已通过 Admin 对外网关完成 `tools/list`、`tools/call`、统计、密钥轮换、停用和过期联调。Harness 员工 OIDC 连接已在 Admin 本地真实网关完成 scope、用户可见性、`tools/list`、`tools/call`、按员工统计及撤权即时生效的验证；独立企业插件已安装到本机 Web 测试 profile，并完成真实员工 OAuth 登录及一次 Host 到 Admin 的成功工具调用。多标签授权请求排队的长期处理、Web 端真实撤权／刷新和桌面 Host 验收仍待完成。默认关闭源码部署；运行容器默认断网，不支持连接级环境变量，因此“独立凭据实例”和需要访问业务系统的托管 MCP 仍未完成。管理页独立显示容器进程状态与 MCP 握手/工具发现结果。
5. 补 SSE 对外兼容和 Stdio 本地桥接、更多 MCP 扩展；根据实际需要再做上游用户委托 OAuth。每阶段同步测试、OpenAPI 和部署文档；不自动改动 Harness 官方核心，优先独立企业集成。

验收至少覆盖：同一服务两条连接使用不同密钥互不串扰；Harness 的两名员工/部门可见性与调用权限不同且撤权即时生效；开发者连接只按连接统计；无鉴权连接仍可统计但不伪称知道调用者；过期/停用/轮换立即拒绝；工具调用失败可定位且不泄密；Web 与桌面端的员工无需逐项手动配置。

## 九、需要确认的实施选择

已确认的默认方式：新建开发者连接默认要求鉴权，管理员可主动选择无鉴权；建议每个应用/项目分别创建连接，但不强制一对一，允许多个应用共用连接，并在界面说明共用时统计合并、密钥轮换和停用会一起影响它们。首批先把 Streamable HTTP 对外打通；SSE、Stdio 本地桥与高级 MCP 能力后续交付。生产环境可使用容器隔离，第三方源码部署以此为边界；若未来要求不使用容器，则需要重新设计安全限制。
